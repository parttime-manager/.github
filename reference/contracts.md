# PTManager API 계약

[요구사항](../spec.md) · [구현 계획](../plan.md) · [데이터 모델](data-model.md)

## 기준과 범위

직원·사장 앱이 서버와 연동할 때 필요한 공통 규약과 호출 흐름을 기록한다. 전체 엔드포인트 목록과 DTO 필드·타입·필수값은 대상 서버의 Swagger UI(`/swagger-ui.html`)와 `/v3/api-docs`에서 확인한다. 로컬은 [Swagger UI](http://localhost:8080/swagger-ui.html)·[OpenAPI JSON](http://localhost:8080/v3/api-docs), 실행 방법은 [Backend README](https://github.com/parttime-manager/backend/blob/main/README.md)를 따른다.

아래는 현재 구현의 동작과 제약이다. 요구사항은 [spec.md](../spec.md), 구현 계획은 [plan.md](../plan.md)를 따른다. Swagger에는 공통 오류와 QR 오류 예시도 있지만, 보안 필터의 응답이나 여러 호출에 걸친 규칙까지 모두 표현하지는 않는다.

## 공통 규약

| 항목 | 규약 |
| --- | --- |
| 호스트 | 로컬 `http://localhost:8080`, 에뮬레이터 `http://10.0.2.2:8080` |
| 업무 API | `/api` 접두사. 아래 경로에는 접두사가 이미 포함되어 있다. |
| 본문 | 기본 `application/json`, 첨부 업로드는 `multipart/form-data` |
| 인증 | `Authorization: Bearer {accessToken}` |
| 날짜·시간 | 날짜 `YYYY-MM-DD`, 시간 `HH:mm:ss`, date-time은 ISO-8601 UTC |

회원가입·로그인·토큰 갱신과 `/actuator/health`는 인증 없이 호출할 수 있다. 그 외 업무 API에는 액세스 토큰이 필요하다. 직원 역할은 `EMPLOYEE`, 사장은 `EMPLOYER`다. 사장 전용 작업은 서버에서 역할을 검사하고 매장 접근은 소속 검증을 거친다. URL의 ID만 바꿔 다른 매장 리소스에 접근할 수 있는 계약이 아니다.

### 응답과 오류

성공 응답의 객체·목록·페이지 구조는 각 API의 OpenAPI 스키마를 따른다. `ApiExceptionHandler`가 처리한 오류는 `ApiError(code, message, timestamp, fields)`를 사용한다. `fields`는 본문 검증 실패(`VALIDATION_FAILED`)일 때 필드별 메시지 맵이고 그 외에는 빈 객체다.

| HTTP | 대표 상황 |
| --- | --- |
| 400 | 본문 검증 실패, 유효하지 않은 QR, 대타 지원·승인 시 시간 겹침 |
| 401 | 로그인·갱신 인증 실패 또는 토큰 누락·만료·무효. 보안 필터에서 처리하는 오류는 `ApiError` 본문을 보장하지 않음 |
| 403 | 역할 불일치, 본인 리소스가 아님, 미소속·매장 접근 권한 없음 |
| 404 | 리소스 없음, 잘못된 초대코드 |
| 409 | 이메일·신청·지원 중복, 이미 처리된 요청, 근무 편성 시간 겹침 |
| 413 | 첨부 용량 초과 |

Swagger가 공통 `ApiError`를 표시해도 보안 계층의 오류 본문이 같다고 가정하지 않는다. 앱은 본문이 없는 인증 오류도 처리해야 한다.

## 인증과 매장 가입

1. `POST /api/auth/signup` 또는 `/api/auth/login` 후 액세스 토큰을 붙인다. 만료 시 `POST /api/auth/refresh`로 갱신한다. 기본 만료는 액세스 1시간, 리프레시 14일이다.
2. 사장은 `POST /api/workplaces`로 매장과 초대코드를 만든다.
3. 직원은 초대코드로 `POST /api/join-requests`를 호출한다. 신청 생성만으로 매장 소속이 되지는 않는다.
4. 사장이 `PATCH /api/join-requests/{id}`로 승인하면 직원의 소속이 설정된다. 승인·거절 결과는 신청자에게 알린다.

사용자는 한 매장에 소속되거나 미소속 상태다. 매장 생성·가입 승인/거절·시급 설정·멤버 방출·QR 발급은 사장 작업이다. 데이터 관계는 [데이터 모델](data-model.md)을 따른다.

Android 앱은 401 응답 시 갱신을 직렬화하고, 다른 요청이 이미 갱신했으면 새 액세스 토큰을 재사용한다. 갱신은 최대 3회 시도하며 실패 사이에 600ms를 기다린다. 갱신 응답이 본문 있는 400/401이면 세션을 지우고, 네트워크 오류·5xx·빈 400/401이면 세션을 유지한 채 원 요청을 실패시킨다. 갱신 후 재시도까지 401이면 반복하지 않는다.

## 근무·근태·인건비

1. 사장의 `POST /api/shifts`는 초안을 만든다. 초안은 직원의 근무 목록에서 제외하고 알림도 생성하지 않는다.
2. `POST /api/shifts/publish`로 기간의 근무표를 발행하면 직원에게 공개하고 해당 직원별로 알림을 만든다. 이미 발행한 근무를 수정할 때도 해당 직원에게 알린다.
3. 직원은 본인 근무에 `POST /api/shifts/{id}/check-in`·`/check-out`으로 QR 출퇴근을 기록한다. 출근은 시작 시각 대비 `PRESENT`/`LATE`로 판정한다. 종료 후 미체크인은 매일 04:00 배치로 `ABSENT` 처리한다.
4. 직원은 `/api/payroll/me`, 사장은 `/api/payroll`·`/api/payroll/weekly`로 인건비를 조회한다. 기간 입력은 `yearMonth`다.

인건비는 조회 시 계산한다. 출퇴근 기록이 모두 있고 퇴근이 출근보다 늦으면 실제 근무 시간, 그렇지 않으면 편성 시간을 사용한다. `ABSENT`는 제외하고 종료 시각이 시작 시각 이하인 편성은 익일까지 이어지는 야간 교대로 계산한다. 현재 시급을 사용하므로 과거 기간의 조회 결과도 시급 변경에 영향을 받는다.

주차별 집계는 매월 1~7일, 8~14일, 15~21일, 22일~말일의 네 구간이다. 월 합계는 직원별 근무 분을 합산한 뒤 시급을 적용하고, 주차 합계는 근무별 금액의 원 미만을 버린 뒤 더하므로 절사 단위에 따라 월 합계와 주차 합계의 합이 다를 수 있다.

### 조회·편성·삭제의 현재 제약

- `GET /api/shifts`는 `employeeId=me` 또는 숫자 ID를 지원한다. `employeeId`가 있으면 직원 기준 조회가 우선하며, `from`·`to`·`status` 필터는 이 경로에도 적용된다. `employeeId`·`workplaceId`가 모두 없으면 빈 목록이다.
- 직원 목록은 발행된 근무만 보여주지만, 상세 조회는 매장 소속만 검사한다. 출퇴근도 본인 근무·매장 소속·QR을 검사하고 발행 여부는 검사하지 않는다. 제품의 초안 비공개 요구사항을 모든 경로에서 보장하지는 않는다.
- 급여 집계는 `ABSENT`만 제외하므로 초안과 미래 편성도 포함한다. 사장 월 집계에는 근무가 없는 현재 직원도 0원으로 포함한다. 직원 급여는 본인 근무만 합산하며 근무가 없으면 현재 시급과 0원·0분·4개 주차를 반환한다.
- 생성·수정의 시간 중복 검사는 같은 직원·같은 날짜의 일반 근무(`endTime > startTime`)끼리만 수행하고 겹치면 409다. 야간 교대와 전날·다음 날 근무와의 충돌은 검사하지 않는다. 대타의 익일 보정 검사와 적용 범위가 다르다.
- 상세 응답의 `workplaceName`은 매장명, `coworkers`는 같은 매장·같은 날짜의 다른 근무자 이름(중복 제거)이다. 동료 목록은 시간 겹침·발행 여부를 검사하지 않는다. `estimatedPay`는 현재 시급 × 편성 시간이며 실근태 급여와 다를 수 있다.
- `DELETE /api/shifts/{id}`는 대기 대타 요청이 있으면 409다. 처리된 대타 요청과 지원 이력은 먼저 삭제하고 근무를 삭제한다.

편성 시각을 출근 판정·결근 배치에 적용할 때는 서버 JVM 기본 시간대를 사용한다. 배치의 04:00도 같은 기준이다. UTC 타임스탬프 저장과 별개이므로 [운영 시간대 설정](deploy.md#2-ec2-초기-설정)을 맞춘다.

## 대타 요청과 승인

1. 직원이 본인 근무에 `POST /api/swap-requests`로 요청한다. 근무당 대기 요청은 최대 1건이다.
2. 다른 직원이 `POST /api/swap-requests/{id}/applications`로 지원한다. 요청자 본인 지원과 중복 지원은 거부한다.
3. 사장이 `POST /api/swap-requests/{id}/approve`로 지원자 한 명을 선택하거나 `/reject`로 거절한다.
4. 승인은 선택 지원을 `APPROVED`, 나머지를 `REJECTED`로 바꾸고 근무자를 재배정한다. 원 요청자는 이력으로 보존하며 요청자와 승인된 지원자에게 결과를 알린다. 거절 결과는 요청자에게 알린다.

지원·승인 시 같은 근무일의 시간 겹침을 검사하고 야간 교대를 보정한다. 지원할 때는 다른 요청에 낸 `PENDING` 지원도 고려한다. 현재 구현은 지원 상태를 기준으로 조회하므로 원 요청이 거절됐더라도 지원 상태가 `PENDING`으로 남아 있으면 검사 대상에 포함된다. 승인은 대기 상태에 대한 조건부 갱신과 단일 트랜잭션으로 처리하며 이미 처리된 요청과 충돌하면 롤백한다.

목록의 필수 `view`는 다음 의미다. 화면은 의도한 값을 명시한다.

| 값 | 조회 관점 |
| --- | --- |
| `open` | 지원 가능한 대기 요청, 본인 요청 제외 |
| `mine` | 내가 요청한 내역, `status`로 추가 필터 |
| `pending` | 대기 요청 전체 |
| 그 밖의 값 | 매장 전체 요청 |

## QR 출퇴근

사장이 `GET /api/workplaces/{id}/qr-token`으로 발급한 값을 직원의 출퇴근 요청에 전달한다. 형식은 `wp{workplaceId}:{epochSeconds}:{HMAC-SHA256 서명}`이다. 서버가 매장과 서명을 검증하므로 앱에서 값을 조합하거나 변경하지 않는다.

### 검증과 모드

매장·서명 일치, 유효 시간, 최신 발급 시각 일치를 확인한다. 서명은 상수 시간 비교를 사용한다. `QR_MAX_AGE_SECONDS`의 현재 설정 기본값은 60초이며 0 이하이면 유효 시간 검사만 생략한다.

| 모드 | 사용 방식 | 유의점 |
| --- | --- | --- |
| 회전형: 양수 | 사장 앱이 토큰을 주기적으로 받아 QR을 갱신 | 유효 시간이 지났거나 더 늦은 시각의 토큰이 발급되면 기존 토큰은 거부됨 |
| 정적: 0 | 한 번 발급해 인쇄·게시 | 최신 발급 검사도 수행하므로 이후 다른 시각에 재발급하면 기존 인쇄물은 무효화됨 |

사장 앱의 QR 화면은 화면이 보이는 동안 45초마다 발급하며 오류 시 5초 뒤 재시도한다. 공기계 고정 모드에서도 갱신은 계속되므로 정적 QR 설정과 화면 고정은 별개다. 정적 QR 인쇄물을 유지하려면 해당 매장에서 QR 화면 등으로 재발급하지 않아야 한다. 양수 수명을 바꿀 때는 앱의 고정된 45초 갱신 주기도 함께 확인한다.

### 저장과 재발급 제약

토큰 자체는 DB에 저장하지 않고 최신 발급 시각만 서버 메모리에 둔다. 재시작 후 발급 기록이 없으면 최신 발급 검사만 통과하며 매장·서명·설정된 유효 시간 검사는 계속한다. 여러 인스턴스는 기록을 공유하지 않는다. 시간은 초 단위여서 같은 초에 다시 발급하면 같은 토큰이 된다.

## 공지와 인수인계

공지 작성·삭제·첨부 업로드는 사장 작업이다. 피드 조회만으로 공지 읽음이 갱신되는 것으로 가정하지 않는다. 공지 탭 진입 시 `POST /api/notices/read`로 읽음을 기록하고 `/api/notices/unread`로 레드 닷을 확인한다.

공지 읽음은 사용자별 마지막 읽은 시각으로 판단하며 공지별 열람자 목록을 제공하지 않는다. 알림 인박스의 읽음 상태와도 별개다. 인수인계는 매장과 `category`로 목록을 조회하며 재고·기기·손님 분류를 사용한다.

첨부는 먼저 `POST /api/notices/attachments`에 multipart 필드 `file`로 업로드하고, 반환된 `fileUrl`을 공지 생성 본문의 `attachmentUrls`에 넣는다. 업로드만으로 공지 첨부 DB 행이 생기지는 않는다. 공지 삭제는 첨부 DB 행을 정리하지만 S3 객체를 삭제하지 않으며, 업로드 후 공지 작성을 취소한 파일도 자동 정리하지 않는다.

## 알림 적재와 푸시

도메인 이벤트가 `notification` 행(인박스)을 만들고, 커밋 후 FCM 푸시 이벤트를 발행한다.

| 이벤트 | 수신자 | `type` | `targetType`/`targetId` |
| --- | --- | --- | --- |
| 공지 작성 `POST /api/notices` | 매장 전원 (작성자 제외) | `NOTICE` | `NOTICE` / `notice.id` |
| 대타 요청 `POST /api/swap-requests` | 매장 **직원(EMPLOYEE)** (요청자 제외) | `SWAP_REQUEST` | `SWAP_REQUEST` / `swapRequest.id` |
| 대타 승인 `.../approve` | 요청자 + 승인된 지원자 (2건) | `SWAP_RESULT` | `SWAP_REQUEST` / `swapRequest.id` |
| 대타 거절 `.../reject` | 요청자 | `SWAP_RESULT` | `SWAP_REQUEST` / `swapRequest.id` |
| 가입 승인·거절 `PATCH /api/join-requests/{id}` | 신청자 | `JOIN_REQUEST` | `JOIN_REQUEST` / `joinRequest.id` |
| 근무표 발행 `POST /api/shifts/publish` | 발행된 근무의 직원 (1인 1건) | `SCHEDULE_CHANGED` | `SHIFT` / `null` |
| 발행된 근무 수정 `PATCH /api/shifts/{id}` | 해당 근무자 | `SCHEDULE_CHANGED` | `SHIFT` / `shift.id` |

### 발송 조건

- 근무 생성·초안 수정은 알림을 만들지 않는다. 수정 알림은 이미 발행된 근무에만 생성한다.
- 인박스는 푸시 수신 설정과 관계없이 적재한다. 설정 행이 없으면 푸시 수신을 기본 활성화한다.
- `ATTENDANCE`·`SWAP_APPLICATION`은 열거형과 설정에만 있고 시드를 제외한 생성 경로는 없다. 출퇴근 체크와 04:00 결근 배치는 알림을 만들지 않는다.

| 설정 | 푸시 종류 |
| --- | --- |
| `swapEnabled` | `SWAP_REQUEST`·`SWAP_APPLICATION`·`SWAP_RESULT` |
| `noticeEnabled` | `NOTICE` |
| `attendanceEnabled` | `ATTENDANCE` |
| `joinRequestEnabled` | `JOIN_REQUEST` |
| 별도 설정 없음 | `SCHEDULE_CHANGED`는 종류별 설정과 관계없이 발송 |

실제 FCM 발송에는 서버 활성화와 자격증명·기기 토큰이 필요하다. [외부 연동 설정](deploy.md#4-fcms3와-앱-연결)을 따른다.

## 변경할 때

경로·DTO 변경은 컨트롤러와 DTO에 반영하고 `/v3/api-docs`에서 확인한다. 권한·호출 순서·상태 전이·알림 수신자가 바뀌면 이 문서를 갱신하고 직원·사장 앱의 호출·응답 모델을 맞춘다. DB 변경은 [데이터 모델](data-model.md)의 기준을 따른다. 서버와 앱은 독립 저장소이므로 관련 변경의 배포 순서도 함께 확인한다.
